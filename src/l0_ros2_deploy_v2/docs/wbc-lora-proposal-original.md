# RK3588 WBC 网络 LoRA 动态加载部署方案

> 用途：交付本地开发 Agent，指导现有机器人 WBC 网络的 RK3588 部署代码改造。
>
> 目标链路：PyTorch `.pt` → ONNX → RKNN → RK3588 C/C++ Runtime。
>
> 状态：总体方案；其中动态矩阵算子的 RKNN 编译和 NPU 执行能力需要基于实际 SDK/固件验证。

## 1. 背景与目标

当前 WBC 策略网络可近似理解为 **7 层、每层 1024 节点的全连接网络**，已有 LoRA 适配器，采用 `.pt → ONNX → RKNN` 部署到 RK3588。

本次改造的核心目标是：**仅保留一份基础 RKNN 模型，将不同策略的 LoRA 权重作为独立的小型参数包存储，并允许 RK3588 在运行时加载、切换适配器，而不重新编译或初始化基础模型。**

### 必须满足的边界

1. **不修改 LoRA 的训练结构和数学语义**：不改变注入层、Rank、Scaling、参数布局对应关系和激活函数的位置。
2. **不拆分基础网络**：优先保持完整 WBC 网络为一个 RKNN 推理图。
3. **不为每套策略保存一份完整 RKNN**：基础模型只保存一份，差异部分以独立适配器文件存储。
4. **不在实时控制线程中进行文件 IO、参数解析、内存分配或模型重新初始化**。
5. **不对底层 RKNN 权重内存进行未经确认的原位改写**：优先通过计算图显式输入注入 LoRA 权重。
6. **不允许静默改变执行后端**：如果发生 CPU 回退、格式不支持或性能退化，应明确记录与报告。

## 2. 总体架构

```text
                   开发主机：离线构建
  ┌─────────────────────────────────────────┐
  │  PyTorch 基础网络 + 现有 LoRA 结构       │
  │     │                                   │
  │     ├─ 导出动态输入 ONNX                 │
  │     │       └─ 转换为 base_lora.rknn     │
  │     └─ 导出各套 LoRA 参数包              │
  └─────────────────────────────────────────┘
                       │
                       ▼
                 RK3588 本地存储
  ┌─────────────────────────────────────────┐
  │  base_lora.rknn   （一份，共用）          │
  │  adapters/                              │
  │    ├─ policy_A/{weights.bin,manifest}   │
  │    ├─ policy_B/{weights.bin,manifest}   │
  │    └─ policy_C/{weights.bin,manifest}   │
  └─────────────────────────────────────────┘
                       │
                       ▼
                  RK3588 Runtime
  ┌─────────────────────────────────────────┐
  │  RKNN Context（初始化一次、持续驻留）     │
  │               ▲                         │
  │  AdapterManager ── 加载 / 校验 / 双缓冲  │
  │               │                         │
  │       安全点提交适配器切换               │
  │               ▼                         │
  │  单个 RKNN 图：Base FC + LoRA 残差      │
  │               │                         │
  │             WBC 输出                    │
  └─────────────────────────────────────────┘
```

关键设计是：**LoRA 的 `A`、`B` 在导出的 ONNX 中是模型运行时输入，而非编译期常量或 initializer**。因此 RKNN 基础图固定，而各套适配器参数可以独立变化。

> **可行性门槛**：RKNN Toolkit2 / Runtime 是否支持目标拓扑中的双动态输入矩阵乘法，并且是否在 RK3588 NPU 上执行，需要先做单层验证。ONNX 支持 `MatMul` 不等于目标 RKNN 图一定支持动态权重矩阵。未通过时不能承诺完整方案可用。

## 3. 模型数学结构与导出要求

对于第 \(l\) 个注入 LoRA 的全连接层：

\[
 h_{l+1}=\sigma_l\!\left(W_l h_l+b_l+\frac{\alpha_l}{r_l} B_l A_l h_l\right)
\]

其中 \(W_l\)、\(b_l\) 是基础模型固定参数；\(A_l\in\mathbb R^{r_l\times d_{in,l}}\)、\(B_l\in\mathbb R^{d_{out,l}\times r_l}\) 是适配器参数。

### 3.1 导出层改造

只修改**推理导出包装层**，不修改已有 LoRA 的训练实现。需要保证：

- 网络原始输入仍为 WBC 状态/观测输入；输出仍保持现有控制输出接口及含义。
- 每个注入层的 `A`、`B` 作为 ONNX 显式输入（可选适度打包，但不能改变其语义）。
- 基础权重与 bias 固定在模型中；LoRA Scaling 保持与训练时一致。
- 导出图中保留 `base(x) + scale * B(A(x))` 的真实依赖，避免导出优化器将 LoRA 分支常量折叠。
- 参数名称、形状、顺序、dtype 与部署参数包的 manifest 一一对应。
- 如果当前模型含归一化、残差、非线性或特殊层，必须严格维持真实前向顺序，不能机械套用 7 层等宽 MLP 近似。

### 3.2 构建流程

```text
原始 PyTorch + LoRA 权重
   ├─ 生成含动态 LoRA 输入的 ONNX
   │     ├─ ONNX Runtime 精度对齐
   │     └─ RKNN Toolkit2 转换
   │           ├─ 首先验证 FP16/非 INT8 的基本功能
   │           └─ 再恢复实际部署量化配置，验证兼容性
   └─ LoRA 参数包导出（每套仅保存差异参数）
```

是否能够将基础网络 INT8 与 LoRA 分支 FP16 混合执行，取决于转换器及设备支持；不能假设其自动兼容。应保留现有量化方案作为目标，并对所有插入点的精度进行检查。

## 4. LoRA 参数包与磁盘存储

推荐布局：

```text
deployment/
├── base_lora.rknn
├── adapters/
│   ├── policy_A/
│   │   ├── weights.bin
│   │   └── manifest.json
│   ├── policy_B/
│   │   ├── weights.bin
│   │   └── manifest.json
│   └── policy_C/
│       ├── weights.bin
│       └── manifest.json
└── runtime_config.json
```

- `weights.bin`：按固定规范连续存储 LoRA `A`、`B` 张量；例如 FP16，明确端序、连续性和对齐方式。
- `manifest.json`：包含参数包版本、基础模型哈希或 ID、适配器 ID、注入层标识、输入张量名、矩阵形状、Rank、Scaling、dtype、字节偏移、总大小、文件校验值。
- 适配器文件不包含基础权重、优化器状态、训练缓存和不需要部署的 checkpoint 信息。
- 参数格式应采用版本化协议，避免模型/适配器不匹配而产生错误控制输出。

### 理论存储计算

假设有 7 个 \(1024\times1024\) 全连接权重矩阵且全部注入相同 Rank 的 LoRA：

\[
P_{base}=7\times1024^2=7{,}340{,}032
\]

\[
P_{LoRA}=7\times(1024r+1024r)=14{,}336r
\]

| 配置 | 纯 LoRA FP16 权重 | 相对基础 FP16 权重 | 额外 MAC 比例 |
|---|---:|---:|---:|
| Rank 4 | 112 KiB | 0.78125% | 0.78125% |
| Rank 8 | 224 KiB | 1.5625% | 1.5625% |
| Rank 16 | 448 KiB | 3.125% | 3.125% |
| Rank 32 | 896 KiB | 6.25% | 6.25% |

基础权重理论大小：INT8 约 **7 MiB**，FP16 约 **14 MiB**。这些是权重体积，不代表最终 `.rknn` 文件、工作区或系统内存占用。

如果共存储 \(K\) 套策略，理论磁盘空间近似为：

\[
S_{shared}\approx S_{base.rknn}+\sum_{k=1}^{K} S_{adapter,k}
\]

相比逐策略保存完整 RKNN，节省量需要以实际生成的 `.rknn` 和 `weights.bin` 文件为准；尤其当基础网络使用 INT8、LoRA 使用 FP16 时，两者的每参数字节数并不相同。

## 5. RK3588 动态加载与切换机制

### 5.1 AdapterManager 责任

在当前 C/C++ 部署工程中增设适配器管理模块，对外提供清晰的语义接口，例如：

```cpp
// 示意 API，具体命名由 Agent 按项目风格确定。
bool preload_adapter(const std::string& path);
bool activate_adapter(const std::string& adapter_id);
std::string active_adapter_id() const;
```

负责以下任务：

1. 初始化并保持唯一 RKNN Context。
2. 按 manifest 验证适配器与基础模型的兼容性。
3. 从磁盘读取 LoRA，完成必要的 dtype/布局转换。
4. 将参数写入**非活动缓冲区**，进行所需的 CPU/NPU 内存同步。
5. 在推理安全边界切换参数版本；在切换完成前不得复用旧缓冲区。
6. 新参数加载、校验或切换失败时保持旧版本继续工作。
7. 提供切换耗时、模型版本、错误信息和内存统计。

### 5.2 缓冲与运行时接口

优先评估使用 RKNN Runtime 的内存管理接口（如 `rknn_create_mem`、`rknn_set_io_mem`，以及 SDK 支持时所需的 `rknn_mem_sync`），实现 LoRA 输入缓冲区复用和低拷贝推理。具体接口签名、缓冲区可写性、同步语义及输入重新绑定行为均以目标 RKNN Runtime 版本为准。

**不要假设**：

- 直接覆盖 `.rknn` 内部权重即被 NPU 识别；
- `rknn_set_weight_mem()` 具备任意编译后权重的热更新语义；
- 运行中的推理可以安全地与输入缓冲区写入并发；
- 更换输入 buffer 绑定一定无性能代价。

建议采用预分配双缓冲 + 明确的推理完成同步点：

```text
当前推理 → 使用 Adapter A 缓冲区
后台线程 → 将 Adapter B 读入备用缓冲区并完成校验
安全切换点 → 更新下次推理使用的适配器版本/输入绑定
后续推理 → 使用 Adapter B
              旧 Adapter A 在无在途读取后可复用
```

不得在当前正在被设备读取的参数缓冲区上直接覆盖 LoRA 数据。若实际 RKNN API 无法安全切换设备输入缓冲，需由 Agent 查明支持方式并明确报告，不可通过不受控并发写入替代。

### 5.3 实时控制约束

- 控制线程不得执行磁盘读取、JSON 解析、参数转置、重新初始化 RKNN 或大块内存分配。
- 切换生效应有确定的安全边界，避免单次前向中混用两套适配器。
- 加载失败、校验失败、版本不匹配时保留旧参数，不影响正在运行的控制循环。
- 切换后的控制输出可能出现跳变；应遵循现有 WBC 的切换/安全状态机，不在本次任务中擅自改变控制策略数学结构。

## 6. 计算开销与内存影响

对于一个 \(d_{out}\times d_{in}\) 的 LoRA 注入线性层，在相同 MAC 口径下：

\[
C_{base}=d_{out}d_{in},\qquad
C_{LoRA}=r(d_{in}+d_{out})
\]

7 层等宽 1024、Rank 8 的近似值：

- 基础网络：**7.34 M MAC / 次前向**。
- LoRA 增量：**0.115 M MAC / 次前向**。
- 理论计算量增幅：**1.5625%**。
- 单套 FP16 LoRA 原始权重：**224 KiB**。
- 两份双缓冲原始权重：**448 KiB**（不包括运行时额外工作区）。

**理论 MAC 比例不等于真实推理延迟比例。** RK3588 上的实际影响可能由动态 MatMul 的 NPU 编译方式、小矩阵利用率、算子调度、精度转换、输入同步与中间张量工作区主导。

需分别测量两个不相同的指标：

- **推理增量**：`T_infer(dynamic_LoRA) - T_infer(base)`，包含适配器激活期间每次推理的真实开销。
- **切换增量**：适配器从存储加载/准备/生效各阶段耗时，以及切换时对控制线程 P99/Pmax 的影响。

系统内存也应区分：基础 RKNN Context、激活适配器、备用适配器、模型工作区、额外 ONNX/RKNN 中间张量、暂存文件缓冲区。不能只以 LoRA 文件大小估算峰值 RAM。

## 7. Agent 实施任务

### 阶段 A：最低成本的兼容性验证

基于现有真实 LoRA 注入层，构造一个**动态 A/B 输入**的最小 ONNX/RKNN 测试：

1. 固定基础线性层权重，将 A/B 作为图输入。
2. 验证 ONNX Runtime 的数值结果与 PyTorch 一致。
3. 使用项目目标 RKNN Toolkit2 版本转换为 RKNN，在 RK3588 真机运行。
4. 不重建 RKNN Context，替换 A/B 输入并验证输出变化。
5. 确认执行后端、延迟、是否出现额外 CPU 计算及错误日志。

**阶段 A 未通过，不继续承诺后续完整部署。** 如 RKNN 对动态 MatMul 不支持，提交可复现的最小模型、转换/运行日志、目标 SDK 版本及阻塞位置，由项目方决定替代路线。Agent 不自行改变 LoRA 注入结构。

### 阶段 B：集成完整动态模型

- 基于现有模型加装推理导出 wrapper，生成统一 ONNX / RKNN。
- 实现 LoRA 参数包导出、manifest 校验与模型 ID 绑定。
- 实现板端 C/C++ AdapterManager、预分配缓冲、参数加载、切换、回退。
- 复用原有 WBC 输入/输出与 RKNN 推理框架；对外增加适配器加载/激活接口。
- 沿用项目现有量化配置，必要时为兼容性验证创建单独构建配置，但不直接改变正式部署量化策略。

### 阶段 C：最小验收测试

以至少两套数值不同、结构相同的 LoRA 权重执行：

| 检查项 | 验收要求 |
|---|---|
| 功能一致性 | PyTorch、ONNX、RKNN 的输出误差在项目规定阈值内；误差阈值结合控制业务确定 |
| 动态加载 | 不重编译 ONNX/RKNN、不重建基础 RKNN Context 即可切换适配器 |
| 不同适配器 | 两套 LoRA 切换前后输出与各自离线参考结果一致 |
| 实时安全 | 当前推理不读取被并发覆盖的参数；切换失败保持旧版本 |
| 性能 | 记录平均、P95、P99、最大延迟；记录磁盘加载、准备、激活耗时 |
| 存储 | 比较一份基础模型 + N 份 LoRA 与 N 份完整 RKNN 的实测大小 |
| 内存 | 比较常驻 RSS/设备相关内存、峰值 RAM、双缓冲开销；检查重复切换泄漏 |
| 执行后端 | 明确确认 LoRA 路径真实由何种设备执行，禁止无记录 CPU 回退 |

性能比较至少包含：

1. 当前原始静态 RKNN 推理。
2. 新动态 RKNN（LoRA 输入已准备、适配器稳定激活）。
3. 新动态 RKNN（加载并切换适配器时）。

所有测量均使用相同的实际 WBC 输入形状、线程/核绑定策略、NPU 配置和量化条件；若条件不同，应在报告中明确标识。

## 8. 明确的非目标与风险

**不属于本轮任务：** 重训 LoRA、更换 Rank、只保留最后一层 LoRA、把七层模型拆成多个 RKNN、将 LoRA 改由 CPU/GPU 执行、为每个适配器制作完整 RKNN、重构 WBC 控制算法。

需优先处理的风险：

- RKNN 不接受所需动态权重 MatMul / NPU 执行受限。
- ONNX 导出或优化环节将 A/B 固化。
- 量化方案改变残差精度或引入格式转换。
- 动态输入数量增多造成调用及内存同步开销。
- 实时线程与后台加载线程在输入缓冲区上发生竞争。
- 切换适配器时控制输出出现瞬态突变。

## 9. 最终交付物

本地 Agent 应交付：

1. 动态 LoRA ONNX 导出代码及对应 RKNN 构建配置。
2. LoRA 适配器独立导出工具与参数包格式说明。
3. RK3588 端动态加载/切换管理代码，并接入现有 WBC 推理路径。
4. 最小功能验证及性能对比结果（含 SDK 版本、设备环境、测试条件）。
5. 若 RKNN 动态 MatMul 存在阻断：最小复现、错误日志、根因及未完成项清单。

**最终架构边界：一份常驻、可复用的基础 RKNN 计算图 + 可独立分发、按需加载并安全切换的 LoRA 参数包。LoRA 的训练实现与数学结构保持不变。**
