## 1 LoRA 相关改动

### L1 新版如何加载 base_ckpt 与 lora_ckpt

**原来：** `prepare_wbc_deploy.py::prepare()` 接收每个动作的完整导出包，校验该动作 checkpoint/ONNX/reference 的身份，打包成独立 `policy.onnx` 与 `reference_motion.onnx`。运行时加载已经编译的 policy，不读取训练 checkpoint。

**现在：** checkpoint 的读取发生在训练交付处理/导出阶段，入口是 `scripts/export_wbc_lora.py::export_delivery()`。`checkpoint()` 使用 `torch.load(..., map_location="cpu", weights_only=False)`：

1. 固定读取 `<训练目录>/base/base_ckpt.pt` 的 `policy`，取其中 `actor` 与 `vecnorms`；同时读取 `base/policy.onnx`、`base/policy.yaml`。
2. `topology()` 检查七个 Linear、五个 LayerNorm/Mish 的形状、图连接、权重、bias、归一化与 Base checkpoint 一致，再建立参数 schema。
3. LoRA checkpoint 路径由 `emotion_index.json` 的 `adapter` 字段指定，**代码没有硬编码必须叫 `lora_ckpt.pt`**。`generate_wbc_emotion_index.py` 扫描 `lora/*/*` 下的训练轮次文件并生成路径及哈希；实际选取以索引为准。
4. `adapter_state()` 要求格式为 `mimic_lite_lora_adapter_v2`，`base_sha256` 匹配，`rank=16`、`alpha=16`，层名、31 张量形状及归一化一致。它用 `W_base + B @ A` 重建 actor 作导出校验；可选完整最终 checkpoint 存在时再核对重建结果。这里 alpha/rank=1。
5. `dynamic_model()` 保留 Base 固定矩阵和归一化，将 LoRA A/B、完整 bias、LayerNorm gamma/beta 变成运行时输入。`export_adapter()` 将各动作参数按 64 字节对齐写入 FP16 little-endian `weights.bin` 和 manifest。

| 参数 | 内容 | 数量与形状 |
| --- | --- | --- |
| 每层 LoRA A/B | 相对 Base 线性权重的低秩增量 | 7 组；A 为 `[16,in]`，B 为 `[out,16]` |
| 每层 bias | 当前动作的完整 bias，不是 bias 差值 | 7 个 `[out]` |
| LayerNorm gamma/beta | 当前动作的完整仿射参数 | 5 组，各 `[1024]` |
| 合计 | A/B/bias 为 21 个，gamma/beta 为 10 个 | 31 个参数张量；加两项观测共 33 输入 |

七层 `(out,in)` 为 `(1024,639)`、`(1024,1024)`、`(1024,1024)`、`(1024,1423)`、`(1024,1024)`、`(1024,1024)`、`(21,1024)`。Base 线性权重固化在共享图中；每次运行不会重新合并并导出完整策略。

**纯 Base 动作：** 使用 `--base-actions` 显式选择。A/B 置零，bias 和 LayerNorm 保留 Base 的完整值，manifest 标记 `parameter_source=base`。文本模式的 `A-C04_mod` 采用此方式；缺失 LoRA 文件不会自动退化成 Base。通用 `process_wbc_lora_delivery.py` 入口没有 `--base-actions` 参数，制作包含纯 Base 动作的包应使用下节显式导出命令。

**目的：** 用一份共享策略图承载多个动作，避免每个动作交付一套完整固定权重，同时保留可追溯的 Base/归一化/schema 身份。`base_ckpt.pt` 和 LoRA `.pt` 都不会进入板端 WBC 的实时加载路径。

### L2 WBC 如何加载 LoRA 参数并切换动作

**原来：** `RLWbc` 持有单套配置、policy 和 reference；`prepareCallback()` 仅接受配置中的一个 `motion_id`。

**现在的初始化：** `RLWbc::RLWbc()` 读取 `wbc_mode`、`wbc_lora_manifest` 和 `available_wbc_policies`。在 LoRA 模式下创建 `WbcLoraAssets`，只初始化一个 `RknnModel(..., ResidentWbc)` 共享策略上下文。`bindModel()` 按实际 RKNN 名称、形状和 dtype 绑定 33 输入，预分配两套参数槽；每个动作另行加载配置和 reference。固定 Base 权重在共享 RKNN 初始化时加载，adapter 权重在动作 prepare 时读取。

**一次动作切换的实际顺序：**

| 阶段 | 责任函数 | 数据和状态变化 |
| --- | --- | --- |
| 选择动作 | `RLWbc::prepareCallback()` | 仅在空闲时从 `motions_` 查找动作；记录准备代次，选择非活动参数槽。 |
| 读参数与校验 | `WbcLoraAssets::loadAdapter()` | 读取 manifest/weights；校验 Base、归一化、schema、动作、文件哈希、偏移、形状和大小；解包 FP16 为主机浮点缓冲。 |
| 写备用槽 | `parameterInputs()` → `stageResidentParameters()` | 按 RKNN 原生 dtype/stride 打包到备用槽；此阶段不调用设备绑定或设备推理。 |
| 提交 | `commitResidentParameters()` | 等待持有准备/推理互斥条件；先将所有新参数同步到设备，再逐个绑定备用槽。同步失败时旧绑定不变，绑定失败尝试恢复整套旧绑定。 |
| 首帧准备 | `captureFrame()` → `inferAndPublish(..., false)` | 使用新鲜观测初始化历史、yaw anchor，以新动作参数/参考预推理首帧；通过后才返回 prepare 成功。 |
| 激活 | 控制器 `startWbcMotion()` → `activeCallback()` | 控制器读取该动作 gains、等待新的 WBC 命令、再次检查状态，然后通过 active topic 激活。worker 只接受具有有效已准备命令的激活。 |
| 失败/取消 | `prepareCallback()`、`restoreResidentParameters()` | 取消递增代次使在途加载失效；首帧失败恢复前一参数槽、动作、历史、anchor 和命令状态；无法完整恢复时禁止继续推理。 |

参数槽切换与推理共享互斥保护；活动槽不能被准备线程写入。活动、已准备或准备中的动作不会被另一个 START 抢占。切换不重新编译策略、不重新创建共享 policy Context；普通动作 reference 在启动预加载，JSON 动作 reference 在请求时登记。

`WbcLoraAssets` 新增完整资产验证：graph 格式、rank/alpha/精度，Base/源 ONNX/normalization/schema 指纹，RKNN 转换记录，动作/config/reference 绑定，参数 manifest 与权重布局。当前版本还验证 graph 与 adapter 的 `parameter_source` 一致，供 T4/T5 选择纯 Base。

控制器侧同时修正准备取消确认和动作请求竞争：超时后继续保持 cleanup 状态，只有 worker 确认取消后才接受新的准备；动作命令使用非阻塞互斥拒绝并发处理。目的都是让“换参数、换参考、换控制权”作为同一个准备事务生效。

### L3 LoRA 模型如何交付 编译和安装到板端

**原来：** 每个动作一份 policy/reference，分别编译成两个 RKNN。**现在：** N 个动作共享一个 `base_lora.rknn`，每个普通动作保留自己的 `reference_motion.rknn`，因此为 1+N 个模型；`weights.bin` 直接加载，不编译成 RKNN。包含纯 Base 的目录仍是一项动作资产。

```text
训练交付                          编译工作包 model_sources/<包名>
base/base_ckpt.pt                 base_manifest.json
base/policy.onnx       导出       base_lora.onnx → base_lora.rknn + .rknn.json
base/policy.yaml        →         adapters/<动作>/manifest.json + weights.bin
emotion_index.json               actions/<动作>/rl_config.yaml
lora/.../adapter轮次.pt           actions/<动作>/reference_motion.onnx
动作reference.onnx                    → reference_motion.rknn + .rknn.json
```

最终训练交付的 Base 固定权重、adapter 数据和 reference 内部浮点数据采用 FP16；共享图对外 33 个输入和 `action[21]` 仍为 FP32。导出器的 CPU 数值对照属于交付处理，板端 `--build-only` 只建立编译产物及来源记录，不执行 Python Runtime 对照。

以下是供软件端迁移时使用的命令模板，本次文档修订未执行。先将 `ws`、`repo`、`training` 设置为目标路径，并使用新的包名 `wbc_release`：

```bash
# 训练/导出机器：制作同时包含纯Base和LoRA动作的源包
python3 -B "$repo/scripts/prepare_wbc_deploy.py" \
  "$training" "$ws/model_inbox/wbc_release" --mode lora \
  --actions A-C04_mod L0_Hugme --base-actions A-C04_mod --fp16
python3 -B "$repo/scripts/preprocess_wbc_lora_fp16.py" \
  "$ws/model_inbox/wbc_release" "$ws/model_sources/wbc_release"
```

上传 `model_sources/wbc_release`，无需上传训练 `.pt`、训练日志或验证样本。在 RK3588 上设置对应 `ws`、`repo` 后执行：

```bash
/usr/bin/python3 -B "$repo/scripts/batch_convert_onnx_to_rknn_rk3588.py" \
  "$ws/model_sources/wbc_release" \
  --manifest "$ws/model_sources/wbc_release/base_manifest.json" \
  --build-only --log-dir "$ws/records/wbc_release_compile"
/usr/bin/python3 -B "$repo/scripts/prepare_wbc_deploy.py" \
  "$ws/model_sources/wbc_release" \
  "$repo/legged_deploy/policy/l0_v5/wbc_release" --mode install-lora
```

`prepare_wbc_deploy.py::install_lora()` 验证源 ONNX、RKNN、转换记录和参数后，在临时目录完成复制，再发布到新的目标目录。运行目录不复制 ONNX，保存：

```text
src/l0_ros2_deploy_v2/legged_deploy/policy/l0_v5/wbc_release/
├── base_manifest.json
├── base_lora.rknn
├── base_lora.rknn.json
├── INSTALLATION.json
├── adapters/<动作ID>/{manifest.json,weights.bin}
└── actions/<动作ID>/{rl_config.yaml,reference_motion.rknn,
                      reference_motion.rknn.json}
```

colcon build --executor sequential --packages-up-to legged_real legged_controllers \
  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo -DLEGGED_DEPLOY_BACKEND=RKNN \

### L4 WBC 的具体推理过程与旧单 policy 有何不同

每个活动周期仍由 `RLWbc::runLoop()` 按 50 Hz 调用 `inferAndPublish()`，输入和输出的机器人语义保持 21 关节。流程是：

1. `captureFrame()` 检查有效观测、时间戳与 `inference_enabled`，提取角速度、重力方向、相对默认角的关节位置和速度。
2. `makePolicyInput()` 从历史索引 `[0,1,2,3,4,8,16]` 取七帧四类信号，再拼接三帧 actor 历史，得到 `(3+3+21+21)×7 + 21×3 = 399`。
3. `makeCommandInput()` 查询 `[-8,-4,-2,0,1,2,3,4]` 八个参考时刻，以 signal-major 顺序拼接 root position、旋转矩阵前两行和 21 关节参考，得到 `(3+6+21)×8 = 240`。yaw anchor 仍把参考朝向绑定到机器人起始朝向，同一周期仅复用重复的边界帧。
4. 静态模式调用两输入 `RknnModel::run()`；LoRA 模式调用 `runResident()`，31 个参数已经驻留，仅更新 policy/command 两项观测，显式同步后 `rknn_run()`，再同步并读取 `action[21]`。
5. 检查 action 有限性、再次确认观测及推理预算，将 actor 输出转为关节目标，通过已有 `BaseRLController::publishPolicyCommand()` 发布。`PolicyMux` 和硬件桥继续处理实际关节控制。

| 对比项 | 旧单 policy A | 当前静态/LoRA 版本 C |
| --- | --- | --- |
| 模型生命周期 | 单 policy 和单 reference | 静态模式可按动作选模型；LoRA 为一个共享 policy 与多动作 reference，JSON 动作另用内存 reference |
| 观测接口 | 399 与 240 | 两项观测维度与拼接语义保持；LoRA 图额外接收 31 参数输入 |
| policy I/O | 每周期 `rknn_inputs_set` 与普通输出读取 | LoRA 使用常驻原生内存和显式缓存同步；普通静态模式保留 Copy 路径 |
| 参考来源 | 单一 reference RKNN | 普通动作调用当前动作 reference RKNN；文本动作从 `WbcJsonReference` 取同格式数据 |
| 参数更新 | 固定在 policy 中 | 只在 prepare 切换完整参数槽，控制周期内不重读权重文件 |
| 时效与控制链 | 有新鲜观测、预算、prepare/active、done | 保留这些检查，补充取消代次、首帧失败回滚、有效 prepared 命令和分段耗时 |
| 输出后处理 | 先 `clip(actor, ±clip_actions)`，再 `×action_scale + default`；历史保存已裁切 actor | 当前先 `actor×action_scale + default`，再将关节目标限制在 `[-10,10]` rad；历史保留原始 actor |

最后一项是**已有实现中的实际行为差异，不是仅换模型文件**。当前 `[-10,10]` 是输出目标的通用界限，不能作为 l0_v5 各关节机械限位的替代说明；文本 reference 的机械限位校验另见 T5。新旧路径的输入维度相同，也不意味着更换 LoRA 参数后的 action 数值应与原 policy 相同。

`BaseRLController::initBaseTopic()`、`publishPolicyCommand()`、`PolicyMux` 的既有 observation/command 传输函数未因本次集成而新增；它们作为被复用的通信层列在 T3/T4。下面函数表覆盖推理代码本身及被共享的声明文件。

### T1 动作生成模型如何在板端编译和部署

采用本次指定的 `text_to_motion_onnx.zip`，冻结到 `texttomotion/baseline/`。生成端交付包含两个静态神经网络：`qwen_tokenizer.onnx` 和 `inbetweener.onnx`，还包含词表、动作素材和 NumPy 合成实现。**这里不使用 WBC policy/reference 转换器，也不将整条 Python 合成流水线转换为一个 RKNN。**

板端编译调用链为：

```text
baseline/compile.sh
  → baseline/convert_onnx_to_rknn_rk3588.py::main()
  → onnx/deploy_rknn/convert.py::convert()
  → require_toolkit_version() + inspect_model() + checked_file()
  → 对两个ONNX分别执行 compile_one()
  → RKNN.config(rk3588) → load_onnx → build(do_quantization=False) → export_rknn
  → 复制词表、motion_assets、host文件并写 compiled/manifest.json
```

要求 Toolkit2 **2.3.2**；编译过程不调用 `init_runtime`。在目标板端可按下列方式生成一个新的编译目录；当前机器人已有经过验证的 compiled 目录，本文修订不要求重新编译它：

```bash
RKNN_PYTHON=/usr/bin/python3 \
  bash "$repo/texttomotion/baseline/compile.sh" \
  --output "$ws/model_sources/text_to_motion/compiled_new" --build-only
```

`RKNN_PYTHON` 应指向实际安装 Toolkit2 2.3.2 的解释器。编译产物的 manifest 记录源 manifest 哈希、模型哈希、RK3588 目标和 ABI。新工作区复用了已编译模型，并将 RKNNLite 与 Runtime 拷贝到：

```text
model_sources/text_to_motion/
├── compiled/{manifest.json,qwen_tokenizer.rknn,inbetweener.rknn,...}
├── deps/rknnlite/                  推理用RKNNLite2 2.3.2
└── runtime/librknnrt.so            推理用Runtime 2.3.2
```

`text_wbc_generate` 默认用 `/usr/bin/python3`，从自身 ROS 安装目录定位这个工作区，前置 `deps` 并选择本地 Runtime。`board_runtime.py::rknn_lite_class()` 在进程内覆写 SDK 绝对库路径选择。它保留 RKNNLite 依赖，没有激活虚拟环境；NumPy、YAML 和 ROS Python 仍来自板端既有环境。`TEXT_WBC_MODEL_ROOT`、`TEXT_WBC_PYTHON`、`RKNN_RUNTIME_LIB` 可显式覆盖默认值。

### T2 动作生成模型如何被调用及输入输出结构

当前入口是 `ros2 run legged_controllers text_wbc_generate`。它是一次生成事务：解析参数、捕获起始姿态、创建两个 RKNNLite session、生成完整轨迹、释放 session、落盘 JSON；加 `--execute` 时继续走 T3 的提交/执行流程。当前 CLI 每次调用创建并释放会话，不能把它描述为已经常驻的生成服务。

```bash
ros2 run legged_controllers text_wbc_generate \
  --model "$ws/model_sources/text_to_motion/compiled/manifest.json" \
  --bundle "$ws/install/legged_deploy/share/legged_deploy/policy/l0_v5/text_wbc_bundle/base_manifest.json" \
  --mapping "$ws/install/system_command_arbiter/share/system_command_arbiter/config/l0_v5.yaml" \
  --base-action A-C04_mod --text '左手抬起' --seed 42 \
  --output "$ws/records/new_request.json"
```

该例只生成，不执行动作；未给 `--snapshot` 时仍需要已有 worker、控制器反馈及实时观测。`--snapshot` 是显式离线输入，不能与 `--execute` 同用。`--tokens` 提供 head/left/right 三个整数分类 ID，走 web 模式，跳过文本分类。执行模式只允许板端 lite2 后端。

**输入分为三层：**

| 层次 | 输入 | 输出 |
| --- | --- | --- |
| 业务请求 | text 或三个 token；seed；speed 0.1–4.0；return_home；return_frames ∈ {−1,30,60,90}；初始/目标九关节角；机械限位 | 完整 N×9 轨迹、token/material ID、帧数、诊断和最终限位调整 |
| `qwen_tokenizer` 静态 ABI | `input_ids:int32[1,129]`、`padding_mask:int32[1,129]` | `qwen_embedding:float32[1,1024]`、`head_logits:[1,47]`、`left_hand_logits:[1,43]`、`right_hand_logits:[1,43]` |
| `inbetweener` 静态 ABI | `initial_pose:float32[1,9]`、`target_pose:float32[1,9]`、`frame_count:int32[1]` | `motion:float32[1,90,9]`、`output_frame_count:int32[1]`；host 按有效帧数截取，不能把 90 个 padding 帧全部播放 |
| 机器人边界 JSON | 50 Hz、rad、机器人解剖学坐标；生成帧数 2–5,000 | `gmr_upper_body_joint_trajectory_v1`，供 WBC 登记，不是电机命令 |

冻结实现 `fixed_tokenize()` 保留文本原始预处理约定；`RknnMotionPipeline.generate()` 对三组 logits 取 argmax 得到分类，再调用 `MotionComposer.generate()` 从素材库选取并合成动作，过渡片段调用 `_transition()` / inbetweener。它不是直接由 embedding 输出整条机器人轨迹。模型会话用 NPU core 0，`_validated_tensors()` 检查输入输出名字、形状、dtype 和有限值；这些函数均属于冻结复用代码。

`motion_adapter.py` 的机器人边界负责单次输入/输出坐标转换：原交付列为 right-hand、left-hand、head；机器人输出为左臂三关节、右臂三关节、颈 yaw/pitch/roll。双臂交换，shoulder/elbow roll 变号，输入和输出各处理一次。token 顺序始终是 head/left/right；活动部位按 token 是否为零判断，而不是按轨迹是否有变化判断。

`generate_wbc_json.py::make_document()` 输出：

| 字段 | 含义 |
| --- | --- |
| `request_id` | `T_` 加随机标识，后续成为 WBC 的动态 `motion_id` |
| `format/robot/angle_unit/fps/coordinate_contract` | 协议版本、l0_v5、rad、50、robot_anatomical_v1 |
| `joint_names/frame_count/frames` | 九关节顺序；每帧含 `frame_index`、`time=i/50`、九项 `joint_positions` |
| `wbc_start_state` | 完整 21 关节初始状态、root position、wxyz quaternion、采集标记 |
| `root_reference_source/wbc_base_action` | 默认用 worker 的 Base reference；显式 snapshot 模式另行处理 |
| `source_zip_sha256/wbc_base_checkpoint_sha256/wbc_normalization_sha256` | 模型及 Base 来源身份；接收端明确检查 ZIP 与 Base，normalization 字段是来源记录，不能宣称该字段本身在 JSON parser 中单独比较 |
| `model_diagnostics/generation_request/safety_adjustments` | 原请求、分类/素材、推理时间、有效限位与输出裁切统计 |
| `expires_at_ms` | 完整 JSON 发布/登记的时效，生成端设为当前时间加 5 秒 |

### T3 如何接入现有通信架构并与 WBC 通信

新 `RosTransaction` 不新增 ROS msg/srv 类型，复用 `std_msgs/msg/String` 传递 JSON，订阅现有 `PolicyObservation`。没有让 WBC 轮询 JSON 文件，也没有向下位机直接发送生成的九关节帧。

### T4 WBC 如何接收 JSON 以及动作话题如何触发执行

**实际交接顺序：**

| 顺序 | 调用/消息 | 接收方响应 |
| --- | --- | --- |
| 1 | 生成端 `RosTransaction.publish(json_pub, document)` | `json.dumps()` 将完整轨迹放入 `String.data`，发到 `/text_motion/json`。 |
| 2 | `RLWbc::jsonReferenceCallback()` | 检查大小、Base action、取消/重复；构造 `WbcJsonReference`，验证全部帧，然后登记一个以 request_id 为键的 `Motion`。 |
| 3 | `publishJsonStatus(id,"ready",...)` | 表示参考已登记；此时未发送执行该动作的电机命令。 |
| 4 | `RosTransaction.execute()` 收到 ready | 发布 `{timestamp_ms: 当前毫秒, action_id: 同一T_ID}` 到正式动作命令 topic。 |
| 5 | `wbcActionCommandCallback()` → `startWbcMotion()` | 验证命令时效/重复/竞争、Walking/速度/姿态/AMP 有效性，调用现有 `control/policy/wbc/prepare` 服务 START。 |
| 6 | `RLWbc::prepareCallback()` | 找到动态 Motion，确认 JSON 未消费且未过期，选择纯 Base 参数，通过与普通 WBC 相同的首帧准备流程。 |
| 7 | 控制器激活，worker `activeCallback()` | active topic 置 true；worker 进入 50 Hz 推理，以 JSON reference 构造 command_short。 |
| 8 | worker done → 控制器 `wbcMotionDoneCallback()` | 通过 `finishWbcMotion()` 回交 AMP，并发布控制器终态。 |

**WBC reference 的处理：** `WbcJsonReference` 将九关节帧并入捕获的 21 关节初态。腿部与未激活部位保持初态，生成 `10帧保持 + 40帧进入过渡 + N帧动作 + 40帧退出过渡 + 10帧稳定`，共 N+100 帧。`inferReferenceFrame(const Motion&, int)` 为 JSON 分支直接读取内存中的关节/root 数据，输出与 reference RKNN 相同的内部 `ReferenceFrame`；后续 yaw anchor、399/240 构造及策略输出通路共用。

动态文本动作复用 `wbc_json_base_action=A-C04_mod` 的完整 Base 参数、配置和共享 policy，不为每个 JSON 创建 reference ONNX/RKNN，也不进行 FK 重导出和模型编译。JSON 文件本身不是可加载的 LoRA adapter。

**登记与取消约束：** JSON 最大 4 MiB，接收端剩余 TTL 必须在 `(0,10秒]`，prepare 时再次检查。相同请求只消费一次；worker 空闲时最多保留一个仍有效且未消费的动态请求。取消 topic 同时进入 worker 和控制器：worker 使未执行请求失效，控制器的 `textWbcCancelCallback()` 对活动 T_ID 调用正式 `finishWbcMotion()`。生成端等待控制器终态，不把 worker 的取消登记回复当作已执行动作的回交完成。

### T5 生成限位与 root reference 检查调整

**限位目的：** 解决原 composer 限位与机器人 l0_v5 映射不一致导致“模型已推理、JSON 交付失败”。`load_limits()` 和 `full_limits()` 按关节名称读取当前 mapping；`configure_generation_limits()` 为每条 pipeline 独立加载冻结 `motion.py` 的模块实例，将机器人限位转换到模型坐标并注入 `LIMITS/FULL_LIMITS`，替换该 pipeline 的 composer。冻结源码和模型权重不变。

当前 neck_pitch 为 `[-0.349,0.175]` rad。composer 内部的轨迹处理使用九关节映射限位；输出端仍保留 `limit_policy=reject` 默认值，若最终残余越界超过 1e−6 rad 则失败，显式 clip 才允许最终裁切。`safety_adjustments` 只记录最终输出边界的裁切，不代表内部合成过程从未受到约束。C++ JSON parser 再次检查每帧限位和未激活部位姿态。

**root 检查目的：** 原实时生成要求测得合法 root 高度，在无里程计时 z=0 会阻断生成；普通 WBC 则从动作 reference 取得目标 root。当前 `initializeJsonReference()` 在 worker 控制线程启动前，通过正式 `inferReferenceFrame()` 读取 Base 动作第 0 帧并缓存 root position/orientation。实时 JSON 标记 `root_reference_source=wbc_base_action`，C++ 用缓存参考替代测得的 root 目标，因此不再增加测量高度门槛。

IMU 四元数、有限值、新鲜观测、正式控制状态/prepare/activate 检查仍存在。`check_snapshot()` 不再要求测量高度在范围内；显式 `--root-height` 或离线 snapshot 仍使用 snapshot reference，并验证参考高度。生成期间关节变化超过 0.15 rad 或观测门槛失效会丢弃结果；prepare 再复核起始关节匹配。这里复用正式 WBC 的传感器/启动流程，JSON 自身的格式、时效和起始姿态校验仍是额外的数据契约。
