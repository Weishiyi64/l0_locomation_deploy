1 LoRA 相关改动

L1 新版如何加载 base_ckpt 与 lora_ckpt

原来： prepare_wbc_deploy.py::prepare() 接收每个动作的完整导出包，校验该动作 checkpoint/ONNX/reference 的身份，打包成独立 policy.onnx 与 reference_motion.onnx。运行时加载已经编译的 policy，不读取训练 checkpoint。

现在： checkpoint 的读取发生在训练交付处理/导出阶段，入口是 scripts/export_wbc_lora.py::export_delivery()。checkpoint() 使用 torch.load(..., map_location="cpu", weights_only=False)：

  1. 固定读取 <训练目录>/base/base_ckpt.pt 的 policy，取其中 actor 与 vecnorms；同时读取 base/policy.onnx、base/policy.yaml。
  2. topology() 检查七个 Linear、五个 LayerNorm/Mish 的形状、图连接、权重、bias、归一化与 Base checkpoint 一致，再建立参数 schema。
  3. LoRA checkpoint 路径由 emotion_index.json 的 adapter 字段指定，代码没有硬编码必须叫 lora_ckpt.pt。generate_wbc_emotion_index.py 扫描 lora/*/* 下的训练轮次文件并生成路径及哈希；实际选取以索引为准。
  4. adapter_state() 要求格式为 mimic_lite_lora_adapter_v2，base_sha256 匹配，rank=16、alpha=16，层名、31 张量形状及归一化一致。它用 W_base + B @ A 重建 actor 作导出校验；可选完整最终 checkpoint 存在时再核对重建结果。这里 alpha/rank=1。
  5. dynamic_model() 保留 Base 固定矩阵和归一化，将 LoRA A/B、完整 bias、LayerNorm gamma/beta 变成运行时输入。export_adapter() 将各动作参数按 64 字节对齐写入 FP16 little-endian weights.bin 和 manifest。
参数 内容 数量与形状
每层 LoRA A/B 相对 Base 线性权重的低秩增量 7 组；A 为 [16,in]，B 为 [out,16]
每层 bias 当前动作的完整 bias，不是 bias 差值 7 个 [out]
LayerNorm gamma/beta 当前动作的完整仿射参数 5 组，各 [1024]
合计 A/B/bias 为 21 个，gamma/beta 为 10 个 31 个参数张量；加两项观测共 33 输入

七层 (out,in) 为 (1024,639)、(1024,1024)、(1024,1024)、(1024,1423)、(1024,1024)、(1024,1024)、(21,1024)。Base 线性权重固化在共享图中；每次运行不会重新合并并导出完整策略。

纯 Base 动作： 使用 --base-actions 显式选择。A/B 置零，bias 和 LayerNorm 保留 Base 的完整值，manifest 标记 parameter_source=base。文本模式的 A-C04_mod 采用此方式；缺失 LoRA 文件不会自动退化成 Base。通用 process_wbc_lora_delivery.py 入口没有 --base-actions 参数，制作包含纯 Base 动作的包应使用下节显式导出命令。

目的： 用一份共享策略图承载多个动作，避免每个动作交付一套完整固定权重，同时保留可追溯的 Base/归一化/schema 身份。base_ckpt.pt 和 LoRA .pt 都不会进入板端 WBC 的实时加载路径。

L2 WBC 如何加载 LoRA 参数并切换动作

原来： RLWbc 持有单套配置、policy 和 reference；prepareCallback() 仅接受配置中的一个 motion_id。

现在的初始化： RLWbc::RLWbc() 读取 wbc_mode、wbc_lora_manifest 和 available_wbc_policies。在 LoRA 模式下创建 WbcLoraAssets，只初始化一个 RknnModel(..., ResidentWbc) 共享策略上下文。bindModel() 按实际 RKNN 名称、形状和 dtype 绑定 33 输入，预分配两套参数槽；每个动作另行加载配置和 reference。固定 Base 权重在共享 RKNN 初始化时加载，adapter 权重在动作 prepare 时读取。

一次动作切换的实际顺序：

阶段 责任函数 数据和状态变化
选择动作 RLWbc::prepareCallback() 仅在空闲时从 motions_ 查找动作；记录准备代次，选择非活动参数槽。
读参数与校验 WbcLoraAssets::loadAdapter() 读取 manifest/weights；校验 Base、归一化、schema、动作、文件哈希、偏移、形状和大小；解包 FP16 为主机浮点缓冲。
写备用槽 parameterInputs() → stageResidentParameters() 按 RKNN 原生 dtype/stride 打包到备用槽；此阶段不调用设备绑定或设备推理。
提交 commitResidentParameters() 等待持有准备/推理互斥条件；先将所有新参数同步到设备，再逐个绑定备用槽。同步失败时旧绑定不变，绑定失败尝试恢复整套旧绑定。
首帧准备 captureFrame() → inferAndPublish(..., false) 使用新鲜观测初始化历史、yaw anchor，以新动作参数/参考预推理首帧；通过后才返回 prepare 成功。
激活 控制器 startWbcMotion() → activeCallback() 控制器读取该动作 gains、等待新的 WBC 命令、再次检查状态，然后通过 active topic 激活。worker 只接受具有有效已准备命令的激活。
失败/取消 prepareCallback()、restoreResidentParameters() 取消递增代次使在途加载失效；首帧失败恢复前一参数槽、动作、历史、anchor 和命令状态；无法完整恢复时禁止继续推理。

参数槽切换与推理共享互斥保护；活动槽不能被准备线程写入。活动、已准备或准备中的动作不会被另一个 START 抢占。切换不重新编译策略、不重新创建共享 policy Context；普通动作 reference 在启动预加载，JSON 动作 reference 在请求时登记。

WbcLoraAssets 新增完整资产验证：graph 格式、rank/alpha/精度，Base/源 ONNX/normalization/schema 指纹，RKNN 转换记录，动作/config/reference 绑定，参数 manifest 与权重布局。当前版本还验证 graph 与 adapter 的 parameter_source 一致，供 T4/T5 选择纯 Base。

控制器侧同时修正准备取消确认和动作请求竞争：超时后继续保持 cleanup 状态，只有 worker 确认取消后才接受新的准备；动作命令使用非阻塞互斥拒绝并发处理。目的都是让“换参数、换参考、换控制权”作为同一个准备事务生效。

L3 LoRA 模型如何交付 编译和安装到板端

原来： 每个动作一份 policy/reference，分别编译成两个 RKNN。现在： N 个动作共享一个 base_lora.rknn，每个普通动作保留自己的 reference_motion.rknn，因此为 1+N 个模型；weights.bin 直接加载，不编译成 RKNN。包含纯 Base 的目录仍是一项动作资产。

训练交付                          编译工作包 model_sources/<包名>
base/base_ckpt.pt                 base_manifest.json
base/policy.onnx       导出       base_lora.onnx → base_lora.rknn + .rknn.json
base/policy.yaml        →         adapters/<动作>/manifest.json + weights.bin
emotion_index.json               actions/<动作>/rl_config.yaml
lora/.../adapter轮次.pt           actions/<动作>/reference_motion.onnx
动作reference.onnx                    → reference_motion.rknn + .rknn.json

最终训练交付的 Base 固定权重、adapter 数据和 reference 内部浮点数据采用 FP16；共享图对外 33 个输入和 action[21] 仍为 FP32。导出器的 CPU 数值对照属于交付处理，板端 --build-only 只建立编译产物及来源记录，不执行 Python Runtime 对照。

L4 WBC 的具体推理过程与旧单 policy 有何不同

每个活动周期仍由 RLWbc::runLoop() 按 50 Hz 调用 inferAndPublish()，输入和输出的机器人语义保持 21 关节。流程是：

  1. captureFrame() 检查有效观测、时间戳与 inference_enabled，提取角速度、重力方向、相对默认角的关节位置和速度。
  2. makePolicyInput() 从历史索引 [0,1,2,3,4,8,16] 取七帧四类信号，再拼接三帧 actor 历史，得到 (3+3+21+21)×7 + 21×3 = 399。
  3. makeCommandInput() 查询 [-8,-4,-2,0,1,2,3,4] 八个参考时刻，以 signal-major 顺序拼接 root position、旋转矩阵前两行和 21 关节参考，得到 (3+6+21)×8 = 240。yaw anchor 仍把参考朝向绑定到机器人起始朝向，同一周期仅复用重复的边界帧。
  4. 静态模式调用两输入 RknnModel::run()；LoRA 模式调用 runResident()，31 个参数已经驻留，仅更新 policy/command 两项观测，显式同步后 rknn_run()，再同步并读取 action[21]。
  5. 检查 action 有限性、再次确认观测及推理预算，将 actor 输出转为关节目标，通过已有 BaseRLController::publishPolicyCommand() 发布。PolicyMux 和硬件桥继续处理实际关节控制。
对比项 旧单 policy A 当前静态/LoRA 版本 C
模型生命周期 单 policy 和单 reference 静态模式可按动作选模型；LoRA 为一个共享 policy 与多动作 reference，JSON 动作另用内存 reference
观测接口 399 与 240 两项观测维度与拼接语义保持；LoRA 图额外接收 31 参数输入
policy I/O 每周期 rknn_inputs_set 与普通输出读取 LoRA 使用常驻原生内存和显式缓存同步；普通静态模式保留 Copy 路径
参考来源 单一 reference RKNN 普通动作调用当前动作 reference RKNN；文本动作从 WbcJsonReference 取同格式数据
参数更新 固定在 policy 中 只在 prepare 切换完整参数槽，控制周期内不重读权重文件
时效与控制链 有新鲜观测、预算、prepare/active、done 保留这些检查，补充取消代次、首帧失败回滚、有效 prepared 命令和分段耗时
输出后处理 先 clip(actor, ±clip_actions)，再 ×action_scale + default；历史保存已裁切 actor 当前先 actor×action_scale + default，再将关节目标限制在 [-10,10] rad；历史保留原始 actor

T4 WBC 如何接收 JSON 以及动作话题如何触发执行

实际交接顺序：

顺序 调用/消息 接收方响应
1 生成端 RosTransaction.publish(json_pub, document) json.dumps() 将完整轨迹放入 String.data，发到 /text_motion/json。
2 RLWbc::jsonReferenceCallback() 检查大小、Base action、取消/重复；构造 WbcJsonReference，验证全部帧，然后登记一个以 request_id 为键的 Motion。
3 publishJsonStatus(id,"ready",...) 表示参考已登记；此时未发送执行该动作的电机命令。
4 RosTransaction.execute() 收到 ready 发布 {timestamp_ms: 当前毫秒, action_id: 同一T_ID} 到正式动作命令 topic。
5 wbcActionCommandCallback() → startWbcMotion() 验证命令时效/重复/竞争、Walking/速度/姿态/AMP 有效性，调用现有 control/policy/wbc/prepare 服务 START。

7 控制器激活，worker activeCallback() active topic 置 true；worker 进入 50 Hz 推理，以 JSON reference 构造 command_short。
8 worker done → 控制器 wbcMotionDoneCallback() 通过 finishWbcMotion() 回交 AMP，并发布控制器终态。

WBC reference 的处理： WbcJsonReference 将九关节帧并入捕获的 21 关节初态。腿部与未激活部位保持初态，生成 10帧保持 + 40帧进入过渡 + N帧动作 + 40帧退出过渡 + 10帧稳定，共 N+100 帧。inferReferenceFrame(const Motion&, int) 为 JSON 分支直接读取内存中的关节/root 数据，输出与 reference RKNN 相同的内部 ReferenceFrame；后续 yaw anchor、399/240 构造及策略输出通路共用。

动态文本动作复用 wbc_json_base_action=A-C04_mod 的完整 Base 参数、配置和共享 policy，不为每个 JSON 创建 reference ONNX/RKNN，也不进行 FK 重导出和模型编译。JSON 文件本身不是可加载的 LoRA adapter。

登记与取消约束： JSON 最大 4 MiB，接收端剩余 TTL 必须在 (0,10秒]，prepare 时再次检查。相同请求只消费一次；worker 空闲时最多保留一个仍有效且未消费的动态请求。取消 topic 同时进入 worker 和控制器：worker 使未执行请求失效，控制器的 textWbcCancelCallback() 对活动 T_ID 调用正式 finishWbcMotion()。生成端等待控制器终态，不把 worker 的取消登记回复当作已执行动作的回交完成。
